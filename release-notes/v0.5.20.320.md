The previous v0.5.15 / v0.5.18 / v0.5.19 fixes tried to coerce
the B station comments endpoint into answering by adjusting
the WBI keys, the buvid3 SPI fetch, and the request metadata.
None of them landed. The cross-reference client the user
flagged is Starfallan/PiliNara, an iOS-side-loadable B station
client that pulls real comment lists from the same
URLSession-based network stack Paladala runs on. Diffing
PiliNara's lib/http/reply.dart + lib/common/constants.dart +
lib/http/init.dart against Paladala's current request shape
surfaced four pieces of metadata that B station's
per-client fingerprint layer appears to gate on, none of
which Paladala was sending in the right shape:

1. User-Agent. PiliNara ships the official B station Android
   HD app UA, not a Safari shape. PiliNara uses
   `Mozilla/5.0 BiliDroid/2.0.1 (bbcallen@gmail.com)
   os/android model/android_hd mobi_app/android_hd
   build/2001100 channel/master innerVer/2001100 osVer/15
   network/2` — this is the one B station's client
   fingerprint layer actually whitelists for non-official
   clients, regardless of platform. The previous iOS-Safari
   Mobile shape (v0.5.19) was close but not the one the
   working client uses. DeviceInfo.userAgent is now pinned
   to the PiliNara Android-HD shape, hard-coded osVer to
   keep the per-install fingerprint stable across iOS
   upgrades.

2. x-bili-trace-id. PiliNara sends the constant
   `11111111111111111111111111111111:1111111111111111:0:0`
   on every request. Without it the server tags the trace
   as a non-official client and gates the payload (200 OK
   with `replies: null`). Added to buildSignedRequest
   alongside the existing `app-key`, `x-bili-aurora-zone`,
   and `env` headers.

3. WBI signature is being REJECTED, not required. PiliNara
   hits the exact same `/x/v2/reply/wbi/main` endpoint
   from the anonymous branch of ReplyHttp.replyList with
   only `pagination_str` + `mode` and no `wts` / `w_rid`
   tokens, and gets the real reply list. With the WBI
   signature Paladala's WbiSignedEndpoint was sending,
   the server returns the canonical silent gate (200 OK
   with valid cursor but `replies: null`). The signature
   tokens are being checked against the same
   per-client fingerprint layer, not the WBI keys
   themselves — invalidate + retry does nothing because
   the rejection is on (UA, app-key, aurora, trace-id),
   not on the WBI keys. Switched WbiSignedEndpoint to
   `signWithWBI: false` and kept the `pagination_str` +
   `mode` query items that PiliNara uses.

Net effect on the chain: legacy pn endpoint already
sends the right shape on Paladala's side, and the WBI
endpoint now also matches PiliNara's anonymous request
shape. The user does not need to log in. If after this
build comments still load as zero replies, the next
candidate to inspect is whether B station's per-account
cookie fingerprinting needs additional SESSDATA-derived
headers beyond what setCookie already injects.
