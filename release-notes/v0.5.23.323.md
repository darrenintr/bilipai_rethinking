AnonymousMainEndpoint must accept .pn(1) cursor


The v0.5.22 build 322 diagnostic showed
`commentsPage(legacy): HTTP success code=0 page.count=2080
replies=0` followed by `commentsPage: endpoint
WbiSignedEndpoint threw (访问权限不足) — continuing`
— but NO `commentsPage(anon-main):` log. The new
endpoint was never reached.

Root cause: the chain walks LegacyPn → AppSigned →
AnonymousMain → WbiSigned, and when the legacy
endpoint silently gates (empty `replies` + non-zero
`allCount`) the orchestrator falls through to the next
endpoint carrying the original `.pn(1)` cursor — it
does NOT translate the cursor between endpoints. My
`AnonymousMainEndpoint` cursor guard rejected `.pn`
cursors with `return nil`, so the orchestrator skipped
it and went straight to WbiSigned, which is the very
/WBI/ path we know returns -403.

The legacy /pn(1)/ start cursor IS the WBI
silent-gate fallback shape (`pagination_str = {"offset":""}`)
— `WbiSignedEndpoint` already accepts it for exactly
this reason. `AnonymousMainEndpoint` should too, since
both endpoints share the same `pagination_str` cursor
shape. Accept `.pn(1)` as `offset = ""`; deeper
`.pn(N)` pages still bail because the pn→offset
mapping is not lossless.

After this fix the chain becomes:
  legacy (empty/silent)
  → appSigned (decline — no access_key)
  → **us (try /main with offset="")**
  → wbiSigned (try /wbi/main with offset="")

So a logged-in user will hit the new anonymous path
before the WBI fallback, and a not-logged-in user
will hit it as their primary path.
