add payload shape + loadComments error logging


v0.5.6 build 306 diagnostic showed 9 successful GET sent 200 OK
with ~93KB body, but 0 commentsPage: returning logs. The
client-side render bug was invisible: the bpLog returning
line never fired but no error was surfaced in the diagnostic
either. The user re-logged in and comments still did not
show, but the request side now demonstrably works (200 OK).

Three changes to make the next diagnostic unambiguous:

1. commentsPage: log the decoded payload shape (upperTop,
   topReplies, replies, cursor with paginationReply.nextOffset)
   immediately after requireOK. The shape log is the single
   most useful signal for "why is the UI empty when the
   response was 200" — the most common cause is that B站
   returns 200 with code: 0 but an empty / null replies
   list (the canonical "unauthenticated viewer" trap).

2. commentsPage: log the merged result count before the
   early-throw for missingIdentity. Without this, the
   "is merged empty because decode produced 0 items" vs
   "merged empty because Task got cancelled" question is
   unanswerable from the diagnostic.

3. loadComments: split the catch into three branches
   (missingIdentity, CancellationError, other) and log
   the actual error type and message in the other branch.
   The previous single catch silently set
   commentsErrorMessage without telling the diagnostic
   what went wrong.

The goal is the next diagnostic clearly attributes a
non-rendering comments panel to one of:
- HTTP / WBI sign failure (already covered by request-side logs)
- Decode failure (covered by decode failed log in get)
- missingIdentity from B站 (covered by new bpLog)
- Cancellation from user navigating away (covered by new bpLog)
- Some other error type (covered by new bpLog)

Memory note: the v0.5.6 "build succeeded but client silent
on decode side" symptom is a reusable diagnostic heuristic
- when server is happy but UI is empty, the missing log is
the first thing to add.
