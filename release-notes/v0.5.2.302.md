auto-bump CFBundleShortVersionString on every prerelease


The build number (CFBundleVersion) was already auto-bumped on
every CI run by reading the latest prerelease tag from the GitHub
Releases API. The marketing version (CFBundleShortVersionString)
was hard-coded — the in-app About page always read whatever was
committed (most recently '0.5.1 TESTING') regardless of how many
builds the CI had shipped. The tag-extraction regex in 'Resolve
release tag' stripped the 'TESTING' suffix, so the prerelease
tags were clean (v0.5.1.301 etc.) but the in-app display was not.

This adds a 'Bump marketing version' step right before 'Bump
build number' that applies the same auto-derive logic to the
marketing version:

  * reads the latest prerelease tag from the Releases API
  * if the tag is v<X>.<Y>.<Z>.<N> (the active line), bumps Z
    to Z+1 for the next prerelease
  * falls back to the committed Info.plist's numeric prefix
    with patch +1 when the API call fails OR the latest tag is
    in a legacy shape (v0.4.<N>, v0.5-beta-ios-<N>, …) — never
    regresses on a single bad run

The new value is written to Info.plist in the runner's working
copy only (no commit, no push) so the latest tag on the server
remains the persistent state — same pattern as the existing
build-number bump.

Trade-off: every push to working ticks the marketing patch
component up by 1 (0.5.1 → 0.5.2 → 0.5.3 …). If the user wants
to ship a real 0.6 / 1.0 release cut, they bump the major/minor
in Info.plist by hand and the auto-derive continues from there.
