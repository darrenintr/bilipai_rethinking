fall back to first acceptQuality qn when selected video id is missing


B站 playurl responses do not always populate the id field on the
selected DASH video track, so playback.selectedVideoQn (resolved
via dash.video.qualityId) is frequently nil. The previous
guard let qn in triggerPrefetchIfPossible silently skipped the
entire Task.detached spawn, which is why build 326 diagnostics
showed serve started with prefetchable true but no subsequent
PlaybackPrefetchManager log line.

Fall back to the first entry of acceptQuality, which is B站's
reported quality ladder. Different qn values get separate cache
entries, so a wrong fallback just causes a one-time re-download
on first quality switch.

Also add bpLog lines on both the skip and fire paths so the next
diagnostic shows whether the trigger fired, and with which qn.
